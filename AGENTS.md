# AGENTS.md

## Project overview

LEGO Manuals is a Symfony 7.4 / PHP 8.4 web application for managing LEGO sets
and their instruction manuals (PDFs). Data lives in an SQLite database plus a
folder of PDF files, both under `public/data` (mounted into the Docker
container as a volume). Core domain: `Set` and `Manual` entities, a small
EasyAdmin-based CRUD backend, an import flow that can autoload manual URLs by
scraping lego.com via a headless-Chrome/Puppeteer script
(`try-to-get-pdf-urls.js`), and a vanilla-JS frontend (`assets/`) for
searching/filtering sets.

## Build & run

- All application commands (composer, console, phpunit, etc.) run **inside
  the Docker container**, not on the host. Assume the container is already
  running.
- Compose files live in `docker/`; run compose commands from within that
  directory. Use `docker-compose.yaml` together with `docker-compose.dev.yaml`
  for local development — beware that `docker-compose.yaml` alone describes
  the production stack (prebuilt image + watchtower auto-updates), not a dev
  build.
  ```
  cd docker
  docker-compose -f docker-compose.yaml -f docker-compose.dev.yaml up -d
  ```
- The project root inside the container is `/var/www/html/`.
- `COMPOSE_PROJECT_NAME=lego` (see `docker/.env`), so the dev container is
  typically reachable as `lego-webserver-1` (or similar; verify with
  `docker ps` if unsure).
- Load fixtures after first start: `php bin/console doctrine:fixtures:load`.
- Frontend assets are built with Webpack Encore (`npm run dev` /
  `npm run watch` / `npm run build`).

## Testing

### PHPUnit (backend)

- Run from inside the container: `APP_ENV=test XDEBUG_MODE=coverage bin/phpunit`.
- Test suite lives in `tests/` (`Unit/`, `Integration/`, `Fixtures/`,
  `Fake/`), configured via `phpunit.dist.xml`, bootstrapped by
  `tests/bootstrap.php`.
- The test environment uses its own isolated SQLite DB
  (`var/test.db`, via `.env.test`) and its own data directory
  (`var/test-data`) — production data under `public/data` is never touched by
  tests.
- Prefer PHPUnit's `@group` feature and run only the relevant group(s) to
  keep test execution fast, when a change only touches one area.
- Use as little mocking as possible. Existing exceptions where a
  fake/mock *is* appropriate (see `TESTING_PLAN.md` for the rationale):
  - `DownloadService` — a `Fake`/interface stands in for real HTTP calls
    instead of hitting external URLs.
  - `PdfService` — use the real fixture PDF at `tests/Fixtures/manual.pdf`
    with the real Imagick/Ghostscript toolchain rather than mocking it.
  - `ImportController::autoload()` — the Puppeteer/Node subprocess call
    against lego.com should be faked, not run for real in tests.
- Mark AI-generated tests with `Generated by AI` (or the
  equivalent for the tool in use) to avoid false positives in review.
- CI runs PHPUnit on every push/PR to `master` via the `test` job in
  `.github/workflows/docker-image.yml` (creates the test DB, runs migrations,
  then `composer phpunit`); the Docker image is only built and pushed once
  that job succeeds.

### Static analysis

- PHPStan: `composer phpstan` (level 4, config in `phpstan.neon`, scans
  `bin/`, `config/`, `public/`, `src/`; `tests/` is currently excluded).
- Rector: `composer rector` (dry-run by default, see `rector.php`).

## Definition of done

After changing code, before considering the work finished:

- All tests must pass: `APP_ENV=test XDEBUG_MODE=coverage bin/phpunit` (run
  inside the container).
- `composer phpstan` must be clean (no errors).

## Coding standards

- All PHP code **must** follow PSR-12:
  - 4-space indentation.
  - Opening braces for classes and methods on their own next line.
  - Control-structure brace placement per PSR-12.
  - Correct line length/spacing and `namespace`/`use` formatting.
- General editor defaults (`.editorconfig`): UTF-8, LF line endings, 4-space
  indent (2-space for `compose*.yaml`), trim trailing whitespace, final
  newline — except Markdown, which keeps trailing whitespace.
- Write all code documentation (PHPDoc, inline comments meant as docs) in
  **German**.

## Project structure

- `src/Entity` — `Set`, `Manual` (core domain, includes filename-generation
  logic such as `getPdfFileName()`/`getCoverFileName()`).
- `src/Repository` — Doctrine repositories (e.g. duplicate-set lookup in
  `SetRepository::doesAlreadyExist()`).
- `src/Service` — `DownloadService` (fetches manual files), `PdfService`
  (cover extraction via Imagick), `ManualService`, `SetLookupService`.
- `src/Controller` — `IndexController` (browse/search), `ImportController`
  (create sets, autoload manual URLs), `StatusController` (health check);
  `Controller/Admin` — EasyAdmin dashboard/CRUD controllers.
- `src/Command` — console commands under `Maintenance/` and `Migrate/`.
- `src/DataFixtures` — production-style fixtures (`AppFixtures`); tests use
  their own lighter fixtures instead.
- `assets/` — vanilla-JS frontend (search/filter, dynamic form rows, AJAX
  autoload against `try-to-get-pdf-urls.js`), built with Webpack Encore.
- `migrations/` — Doctrine migrations.
- `docker/` — Dockerfile, compose files, PHP/Apache/ImageMagick config,
  entrypoint script.
